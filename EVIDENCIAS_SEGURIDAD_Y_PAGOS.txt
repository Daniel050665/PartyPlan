10. PRUEBAS DE SEGURIDAD (4 situaciones)
--------------------------------------------------------------------------------
Se pueden mostrar en el navegador o con curl en PowerShell (curl.exe).

  a) ACCESO A UN ENDPOINT PUBLICO (sin iniciar sesion)
     Navegador: abrir http://localhost:8080/api/publico/planes
     curl.exe -i http://localhost:8080/api/publico/planes
     Resultado: 200 con el catalogo de planes.
     (Comparar: curl.exe -i http://localhost:8080/api/planes  -> 401)

  b) INICIO DE SESION CORRECTO
     App: entrar con juan@gmail.com / juan123 -> llega a "Mis reservas".
     curl.exe -i -u juan@gmail.com:juan123 http://localhost:8080/api/auth/me
     Resultado: 200 {"usuario":"juan@gmail.com","rol":"USER"}

  c) CREDENCIALES INCORRECTAS
     App: entrar con juan@gmail.com / malaclave -> "Usuario o contraseña incorrectos."
     curl.exe -i -u juan@gmail.com:malaclave http://localhost:8080/api/auth/me
     Resultado: 401 {"mensaje":"Credenciales inválidas o sesión expirada."}

  d) ACCESO DENEGADO POR FALTA DE PERMISOS
     curl.exe -i -u juan@gmail.com:juan123 -X DELETE http://localhost:8080/api/planes/1
     curl.exe -i -u juan@gmail.com:juan123 http://localhost:8080/api/usuarios
     Resultado: 403 {"mensaje":"No tienes permisos para realizar esta operación."}
     App: como juan, escribir en la barra http://localhost:4200/usuarios
          -> aviso rojo "No tienes permisos para ver esa página."
     Extra: juan no ve las reservas de maria (GET /api/reservas solo devuelve las suyas).

12. EVIDENCIA DE AUTENTICACION EN CHROME DEVTOOLS
--------------------------------------------------------------------------------
Mecanismo usado: HTTP BASIC, SIN SESION (no usamos JWT ni cookies).

  Network (F12 -> Network -> Fetch/XHR):
    1. Iniciar sesion y abrir cualquier pantalla (ej. Planes).
    2. Clic en la peticion "planes" -> Headers -> Request Headers.
    3. Se ve:  Authorization: Basic anVhbkBnbWFpbC5jb206********
       "Basic" + usuario:contrasena codificado en Base64. Base64 NO es cifrado:
       cualquiera puede decodificarlo, por eso en produccion se usa HTTPS.
       (En la sustentacion, ocultar el valor: no mostrar la cabecera completa.)
    4. La respuesta NO trae Set-Cookie: el servidor no crea sesion (STATELESS,
       B/Config/SecurityConfig.java:137). Por eso el navegador debe enviar la
       cabecera Authorization en CADA peticion.
  Application (F12 -> Application -> Session Storage -> http://localhost:4200):
    partyplan.token    = el valor Base64 (ocultarlo en la sustentacion)
    partyplan.usuario  = juan@gmail.com
    partyplan.rol      = USER
    Lo guarda F/core/auth.service.ts:35. sessionStorage se borra al cerrar la
    pestana. Al cerrar sesion se borran los 3 valores.
  Quien agrega la cabecera: F/core/api.service.ts:33 crearOpciones() en cada peticion.
  Como lo valida el backend: Spring Security lee la cabecera, decodifica el
  Base64, busca el usuario (en memoria o en PostgreSQL) y compara la
  contrasena con BCrypt. Si no coincide -> 401. Si coincide pero el rol no
  alcanza -> 403.

PARTE 2. PAGOS CON WOMPI (laboratorio)
################################################################################

COMO FUNCIONA
  1. En "Mis reservas", una reserva PENDIENTE tiene el boton "Pagar $..."
     (F/pagos/boton-pagar.component.ts).
  2. Angular llama POST /api/pagos/wompi/checkout con { reservaId }.
     El backend calcula el monto con el precio del plan (el navegador NO
     decide el precio), crea la orden PENDING y devuelve el link firmado.
  3. El usuario paga en la pagina de Wompi (Sandbox, dinero de mentira).
  4. Wompi avisa al webhook POST /api/pagos/webhook (si el backend esta en Render)
     y devuelve al usuario a /pago/resultado?id=TRANSACCION.
  5. La pagina de resultado pregunta al backend; el backend consulta a Wompi,
     actualiza la orden y, si fue APPROVED: la reserva pasa a CONFIRMADA y se
     registra el pago como PAGADO con metodo WOMPI.

ARCHIVOS
  Backend (B/pagos/):
    Orden.java                    tabla "ordenes": referencia, monto en centavos, estado
    OrdenRepository.java          guardar y buscar ordenes
    WompiService.java:94          firmaIntegridad(): SHA-256(referencia+centavos+moneda+secreto)
    WompiService.java:99          urlDePago(): link de Web Checkout
    WompiService.java:121         eventoEsValido(): comprueba la firma del webhook
    WompiService.java:163         consultarTransaccion(): pregunta a Wompi

  Frontend (F/pagos/):

PASOS QUE DEBES HACER TU (solo tu puedes crear la cuenta de Wompi)
  1. Crear la cuenta en wompi.co y dejar el interruptor en Sandbox.
  2. Copiar las 4 llaves (comercios.wompi.co -> Desarrollo -> Desarrolladores).
     Todas deben decir "test".
  3. En PartyPlan-main, copiar secretos.properties.ejemplo como secretos.properties
     y pegar las llaves. Este archivo esta en .gitignore: NO se sube a GitHub.
  4. Reiniciar el backend. Sin llaves, el boton muestra
     "Los pagos con Wompi no están configurados...".

TARJETAS DE PRUEBA (Sandbox)
  4242 4242 4242 4242  -> Aprobada
  4111 1111 1111 1111  -> Rechazada
  Fecha: cualquiera en el futuro. CVC: 3 numeros. Nombre: cualquiera.

  DIFERENCIA ENTRE TU COMPUTADOR Y RENDER
  Wompi NO acepta devolver al usuario a una direccion localhost o 127.0.0.1
  (responde 403 "Request blocked"). Por eso:
  - Frontend en tu computador: Wompi se abre en OTRA pestana. La pestana de
    PartyPlan muestra "Completa el pago en la pestaña de Wompi" y cada 3 s
    pregunta GET /api/pagos/wompi/orden/{referencia}. El backend consulta a
    Wompi por la referencia usando la LLAVE PRIVADA (por eso es necesaria).
    (B/pagos/WompiService.java: puedeVolverAutomaticamente() y consultarPorReferencia())
  - Frontend publicado (https): Wompi devuelve al usuario a
    /pago/resultado?id=TRANSACCION en la misma pestana, y ademas llega el
    webhook (registrarlo en Wompi, ver Parte 3).
  Si el navegador bloquea la pestana nueva, Wompi se abre en la misma pestana.
